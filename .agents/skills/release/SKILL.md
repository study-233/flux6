# Flux6 发布

## 发行说明

从 `origin` 上一份公开的 Flux6 正式版比较到本次目标提交，按实际交付的平台筛选变更。标题用 `Flux6 <版本>`。正文用中文，每项用户能感知的变化写一句，只有一项就只写一句。

> macOS 和 Android 新增应用内更新。

仅在用户必须采取操作才能升级时，补一句具体操作。省略开场白、致谢、内部重构、测试记录、提交清单、附件目录和例行安装提示。正文不写 SHA-256、摘要值或校验命令。提交 Release 时使用审定的正文，不追加自动生成的日志。只要求文案时，交付标题和正文即可。

## 准备候选

在仓库根目录运行 `python3 scripts/version.py`，核对本次交付平台的版本与 build。每个版本在 `origin` 共用一个 `v<版本>` 标签和一份 Release。记录目标提交，用同一源码树构建安装包及对应源码，复用已有签名身份，并按平台指南完成构建和安装验收。

| 平台 | 应交付和核对的文件 |
| --- | --- |
| [macOS](../../../apps/macos/README.md) | DMG、对应源码、Sparkle 更新 ZIP 和签名的 `appcast-arm64.xml`。DMG 使用更新 ZIP 中的同一签名 App，清单的文件名、版本和 build 必须匹配。 |
| [Android](../../../apps/android/FREEV6.md) | 上传名为 `Flux6-<版本>-android-arm64.apk` 的签名 APK 和对应源码，核对应用 ID、版本、build 及与上一版一致的签名证书。 |
| [Windows](../../../apps/windows/README.md) | 从目标提交的 Windows 发行工作流取 Tauri x64 NSIS 安装包、对应源码和 `version.json`，核对清单中的安装包地址和摘要。 |

按文件名逐个选取公开附件。构建生成的 `SHA256SUMS`、`Windows-SHA256SUMS`、`*.sha256` 及同类校验文件只用于核验，不上传、不链接，也不将整个产物目录打包上传。保留更新协议依赖的签名和清单字段。

## 更新通道

- 设为 Latest 前，按[更新协议](../../../docs/releases/in-app-updates.md)检查已安装客户端。Android 0.1.1 按 Latest 标签寻找 APK，并先读取同一 Release 的 `SHA256SUMS`。缺少该附件时旧版无法应用内升级，仅修改新 APK 也无法修复旧版。若本次接受手动迁移，验证原签名 APK 可覆盖安装，并在正文给出一句必要操作。升级路径尚未确定时，保留草稿和现有 Latest。
- Windows 也从 Latest 读取 `version.json`。本次未发 Windows 新包时，沿用最近已发布安装包的有效清单。有新包时先核对安装包，再上传对应清单。
- macOS 更新 ZIP 公开可下载且验签通过后，再将同一份已签名清单部署到 `macos-updates`，保持清单字节原样。

## 发布与复核

用户仅要求准备时，交付本地文案和附件清单。执行发布时，先核对远端同名标签的目标提交和已有 Release。可续传同一候选草稿中缺少的文件。遇到标签指向不同提交或同名附件内容不同时，保留原件并报告差异。

先在草稿核对标签、正文和附件名称、大小与本地摘要，再按约定公开并设置 Latest 或预发行状态。公开后从匿名下载地址复核安装包和更新清单。若本次包含[官网](../../../site/README.md)或 Homebrew 分发，使用已公开的附件地址和实际发布时间同步，核对下载入口。交付 Release 链接，另记平台验收结果。
